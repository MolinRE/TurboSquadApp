# «Турбо-Бригада»: как мы работаем вдвоём эти 48 часов

Этот документ — не бюрократия, а три простых инструмента, которые экономят нам время именно потому, что нас двое и оба немного лезем в чужую область (продакт+фронт и бэкенд+фронт-с-помощью-ИИ). Ниже — что это, зачем, и финальный список ИИ-скиллов, которые мы используем.

---

## 1. CONTEXT.md — общий словарь проекта

**Что это:** один файл в корне репозитория, где мы фиксируем, как называются вещи в проекте. Просто список терминов.

**Зачем:** когда ИИ-агент (Claude Code) стартует новую сессию — например, ты открываешь чат в 2 часа ночи, чтобы доделать бэкенд — он не помнит, что было в предыдущих 10 сессиях. Без словаря он либо переспрашивает, либо (хуже) сам придумывает название для того, что уже названо иначе в другом файле. Результат — в одном месте `layaScore`, в другом `evaluationResult`, и это уже баг на ровном месте.

Пример прямо из нашего проекта:

```markdown
# CONTEXT.md

- **Laya-скоринг** — оценка реплики пассажира моделью Laya Engine 
  (критерии choice/score/noul) за ~33мс. Это ОТДЕЛЬНЫЙ вызов, 
  не связанный с генерацией текста ответа через YandexGPT/GigaChat.
- **ЧС** — чрезвычайная ситуация, сценарий Medium-режима, 
  представлен как граф решений (не текст, а дерево вариантов).
- **Вектор развития** — блок в профиле, показывающий динамику 
  4 шкал между разминками.
```

После того как термин тут появился — и ты, и я, и агент говорим "прогони через Laya-скоринг" вместо абзаца объяснений. Это не для галочки: это буквально экономит время печатания и токены на каждой сессии.

**Как появляется:** мы не пишем его вручную. В начале запускаем скилл `grill-with-docs` — это ИИ-интервью, где агент задаёт нам вопросы про продукт, пока не разберётся, и сам параллельно заполняет CONTEXT.md и первые ADR (см. ниже). Наша задача — просто отвечать на вопросы.

---

## 2. ADR — «почему мы так решили»

**Что это:** ADR = Architecture Decision Record. Короткий файл на каждое важное решение: что решили, почему, что отвергли, что это значит дальше. У нас будет папка `docs/adr/`, в ней несколько таких файлов, пронумерованных.

**Зачем:** это не для истории проекта — это защита решения от нас самих же, уставших. Пример:

```markdown
# ADR-003: Laya-скоринг отделён от вызова LLM-генерации

Статус: Принято
Контекст: Hard-режим требует и скор ответа (~33мс), и текст реплики
  от LLM (её латентность непредсказуема). Один синхронный вызов
  делает наш SLA 33мс недостижимым.
Решение: Два независимых параллельных вызова. Скор двигает шкалы 
  сразу, текст реплики подгружается/стримится отдельно.
Последствия: Frontend должен уметь обновлять шкалы раньше, 
  чем появляется текст ответа пассажира.
```

Представь: ты пишешь бэкенд в 3 часа ночи, натыкаешься на этот же код, и он кажется тебе излишне сложным — "зачем два вызова, давай один, проще же". Без ADR ты можешь это молча упростить и сломать SLA, который мы сознательно заложили в архитектуру ещё на старте. С ADR — ты открываешь файл, видишь причину, и либо соглашаешься с ней, либо мы вдвоём осознанно её пересматриваем — но не ломаем случайно.

**Как появляется:** тоже автоматически, из `grill-with-docs` на старте, и дальше по одному ADR добавляется в момент любого спорного архитектурного решения (можно просто попросить агента: "запиши это как ADR").

## 3. Файлы миграций — зачем они важны даже на 48 часов

Ты как бэкендер наверняка и так пишешь миграции EF Core по привычке. Вопрос "зачем это на хакатоне, если можно просто накатить схему через `EnsureCreated` и не заморачиваться" — справедливый. Вот почему миграции всё равно важны именно в нашем случае:

1. **Мы оба меняем схему.** Я иногда трогаю бэкенд с помощью ИИ. Если я поменяю модель локально и просто подгоню свою БД под неё вручную — у тебя на другом компьютере будет другая структура таблиц, и мы это заметим только когда что-то сломается непонятным образом. Файл миграции — это по сути git-коммит для базы данных: применил у себя, закоммитил файл, другой человек подтянул и применил тот же файл — обе базы идентичны.
2. **Откат при поломке.** Если ИИ-агент (или один из нас, уставший) сделает миграцию, которая ломает данные — у нас есть последняя рабочая миграция, к которой можно откатиться, вместо того чтобы разбираться, что вообще сейчас в таблицах.
3. **Деплой перед демо.** В финале (см. таблицу ниже, `babysit`) мы должны выкатить приложение на реальный хостинг за 2-3 часа до дедлайна. Без миграций это значит руками воспроизводить финальную структуру БД на проде под стрессом. С миграциями — одна команда (`dotnet ef database update`) гарантированно даёт ту же схему, что и в разработке.
4. **История для ИИ-агента.** Файлы миграций — это, по сути, тот же CONTEXT.md/ADR, только для базы данных: агент может прочитать их и понять, как менялась схема и почему, вместо того чтобы гадать по текущему состоянию живой БД (которое он не видит напрямую).
5. **Сид-данные для демо не слетают.** Если поздно найдётся, что нужно добавить, например, колонку `confidence` к результату Laya-скоринга — миграция добавляет её инкрементально, не пересоздавая таблицы с нуля и не убивая уже подготовленные демо-данные.

Итог: миграции — это не формальность "как положено", а конкретный механизм синхронизации между нами двумя и страховка перед демо.

## 4. Тикеты — GitHub Issues

Договорились: трекер всё-таки ведём, потому что это не только для порядка, а конкретная польза:

- **Для ИИ-агента** тикет — это явная граница объёма задачи. Без тикета агент сам додумывает, что входит в фичу, а что нет — отсюда лишний код и дублирование.
- **Для нас** тикет — это письменный интерфейс между "что нужно" (обычно формулирую я) и "как реализовано" (обычно делает и объясняет мне это коллега) — особенно важно, раз наши роли не совпадают один в один.

**Как заводим:** любой из нас, через скилл `to-tickets` — не вручную. Говоришь агенту в двух словах, что за фича, он сам раскладывает её на тикеты с чёткими границами и создаёт их в GitHub Issues (не файл, не заметка — реальные Issues, привязанные к репозиторию).

**Как закрываются:** не руками. Когда PR с решением мержится, в его описании пишем `Closes #12` — GitHub сам закрывает тикет. Никакого отдельного действия "не забыть закрыть".

## 5. Финальная таблица скиллов

| Скилл | Источник | Когда используется | Что делает (простыми словами) | Зачем именно нам |
| --- | --- | --- | --- | --- |
| `setup` | sdlc | Час 0, один раз | Настраивает репозиторий: куда класть документы, какие проверки обязательны перед мержем | Не тратим время на споры "куда класть файлы" каждый раз заново |
| `setup-env` | sdlc | Час 0, сразу после `setup` | Проверяет и ставит нужные инструменты разработки (SDK, CLI и т.п.) | Меньше шанса упереться в "у меня не запускается" в середине хакатона |
| `grill-with-docs` | mattpocock | Час 0, один раз | ИИ-интервью про продукт: агент спрашивает, пока не поймёт всё, и сам пишет CONTEXT.md + первые ADR | Снимает с нас саму задачу "сесть и написать документацию" — она появляется как побочный продукт разговора |
| Design OS | design-os | Часы 0–3, с таймером | Отдельный инструмент: продуктовое видение → модель данных → дизайн-система (цвета/шрифты) → экраны с примерами данных | Даёт нам единый визуальный язык до того, как написана первая строчка боевого кода |
| `to-tickets` | mattpocock | На каждую фичу, по мере появления | Превращает короткое описание фичи в тикеты с чёткими границами, создаёт их в GitHub Issues | Явная граница объёма — и для агента, и для нас двоих с разными ролями |
| `to-spec` | sdlc | Только на 2-3 самые рискованные фичи (Hard-чат, интеграция Laya/LLM) | Пишет более подробную техническую спеку решения относительно нашей кодовой базы | Для простых фич — лишний шаг, для сложных — страховка от недопонимания дорогой части системы |
| `prototype` | mattpocock | При необходимости, до финального дизайна Hard-чата | Быстро собирает 2-3 одноразовых варианта интерфейса на выбор, без привязки к финальному коду | Проверяем идею дёшево, прежде чем строить финальную версию |
| `implement` | mattpocock | На каждую фичу | Пишет код по тикету/спеке, попутно гоняя тесты на ключевых местах (`tdd`), и сам запускает `code-review` перед тем как считать работу законченной | Основной рабочий цикл "тикет → готовый, проверенный код" |
| `code-review` | mattpocock | Перед каждым мержем в основную ветку | Проверяет код по двум независимым направлениям параллельно: соответствие стандартам кода и соответствие тому, что реально просили в тикете | У нас нет третьего человека, который читал бы код со стороны — этот скилл и есть наш "второй ревьюер" |
| `resolving-merge-conflicts` | mattpocock | Когда git ругается на конфликт | Разбирает конфликт слияния кусок за куском, ориентируясь на то, что каждый из нас хотел сделать, а не грубо берёт одну версию | Мы оба full-stack и можем случайно задеть одни файлы — конфликты вероятны |
| `ui-kit` | sdlc | Один раз, сразу после экспорта из Design OS | Просматривает уже спроектированные экраны и собирает из них один общий набор компонентов и стилей, убирая дубли | Снимает риск "восьми разных кнопок", которые могли появиться ещё в Design OS |
| `ui-implement` | sdlc | На каждый экран | Строит реальный экран в нашем Next.js-коде, используя только компоненты из общего набора | Гарантирует, что новый экран не придумывает свои кнопки/карточки заново |
| `ui-review` | sdlc | Примерно раз в 12 часов | Сверяет, что реализованные экраны действительно используют общий набор компонентов, без автоправок — просто отчёт | Ловим отклонения от дизайн-системы, пока их немного |
| `diagnosing-bugs` | mattpocock | На любой баг, который не решается за 20-30 минут | Дисциплинированный процесс: сузить проблему → выдвинуть гипотезу → проверить → исправить → написать тест, чтобы не вернулось | Не даёт зависать на баге бесконечно методом "потыкать наугад" |
| `improve-codebase-architecture` | mattpocock | Раз в 10-12 часов | Сканирует весь код проекта и показывает отчёт, где уже накопился беспорядок | Ловим хаос маленькими порциями, а не разгребаем всё в последние часы |
| `handoff` | mattpocock | Когда ОДНА сессия чата с агентом разрослась и стала путаться в контексте | Сжимает длинный разговор в компактный документ, с которым можно начать свежую сессию без потери сути | У нас нет смен между людьми, но долгие сессии всё равно засоряются — это лечит именно это |
| `wizard` | mattpocock | Разовые шаги, которые нельзя доверить агенту целиком | Строит пошаговый интерактивный скрипт для ручных действий: ключи API YandexGPT/GigaChat, деплой, секреты | Такие вещи нельзя автоматизировать вслепую, но можно сделать пошагово и без ошибок |
| `babysit` | sdlc | Финал, примерно час 42-46 | Дожимает оставшиеся ошибки CI и замечания ревью, мержит финальный код по нашей команде | Финишная прямая перед демо — последний чистовой проход |
| `api-contract-first` (наше правило, не готовый скилл) | — | Один раз, в конце архитектурного блока Фазы 1; дальше — только по согласованию вдвоём | Зафиксированная спецификация API (кто что и как вызывает) до начала кода | Раз оба full-stack — легко случайно разойтись в том, что ожидает бэкенд и что шлёт фронтенд |
| `latency-budget-guard` (наше правило) | — | На каждое изменение в зоне Laya-скоринга | Ручная проверка: реальное время ответа скоринга всё ещё укладывается в \~33мс | Единственное, что реально проверит соблюдение нашего жёсткого SLA |
| `llm-resilience-wrapper` (наше правило) | — | Один раз, при первой интеграции YandexGPT/GigaChat | Обёртка вызова: таймаут, повтор при ошибке, заранее заготовленный ответ, если API недоступен | Внешний API может отвалиться именно в момент питча — это наша страховка |

## 6. Установка скиллов — чтобы не пересекались

sdlc ставится целиком (частями нельзя), mattpocock — выборочно:

```bash
# sdlc — целиком
claude plugin marketplace add kulichevskiy/sdlc
claude plugin install sdlc@kulichevskiy --scope project

# mattpocock/skills — выборочно
npx skills@latest add mattpocock/skills
```

При установке mattpocock отмечаем только: `grill-with-docs, to-tickets, implement, code-review, tdd, diagnosing-bugs, prototype, resolving-merge-conflicts, wizard, handoff, improve-codebase-architecture, writing-for-agents`

Не отмечаем: `to-spec` (берём версию sdlc), `grill-me`, `triage`, `wayfinder`, `to-questionnaire`, `wait-what`, `ask-matt`, `teach`, `domain-modeling`, `codebase-design`.

Технически конфликта команд не будет (sdlc — под своим неймспейсом плагина), но его встроенные `to-tickets`/`implement`/`code-review` мы просто никогда не зовём — вместо них всегда версии mattpocock. Это единственное место, где "не пересекаться" — вопрос дисциплины, а не установки, поэтому фиксируем это явно в AGENTS.md ниже.

## 7. AGENTS.md — правила поведения агента

Не путать с CONTEXT.md: там — словарь терминов продукта, здесь — правила поведения агента и процесса. Файл лежит в корне репозитория и подгружается автоматически в начале каждой сессии, вызывать ничего не нужно. Собирается один раз через скилл `writing-for-agents`. Минимальный скелет:

```markdown
# AGENTS.md

## Где что искать
- Словарь терминов: CONTEXT.md
- Архитектурные решения: docs/adr/
- Дизайн-система и компоненты: docs/ui-kit/

## Какую команду звать на каком этапе
- Завести тикет фичи → /to-tickets (mattpocock, пишет в GitHub Issues)
- Расписать сложную/рискованную фичу подробнее → /sdlc:to-spec
- Реализовать тикет → /implement (mattpocock, тянет tdd)
- Проверить перед мержем → /code-review (mattpocock, две параллельные оси)
- НЕ использовать to-tickets/implement/code-review из плагина sdlc

## Жёсткие правила
- Ни одного нового UI-компонента без проверки docs/ui-kit
- Ни одной ручной правки схемы БД — только через миграции EF Core
- Не менять контракт API без явного согласования вслух
- Каждое изменение в зоне Laya-скоринга — проверить latency (~33мс)
- Новая зависимость — сначала сообщение в чат, потом код
- PR закрывает тикет через "Closes #N" в описании
```

## 8. С чего начать

1. Голый скелет репозитория (`create-next-app` + `dotnet new webapi`), закоммитить без фич — иначе `setup` настраивается вслепую.
2. Установка плагинов (раздел 6).
3. `/sdlc:setup` — конвенции, профиль проверки (берём **Basic**).
4. `setup-env` — проверка инструментов.
5. Доводим AGENTS.md через `writing-for-agents`.
6. `grill-with-docs` — один раз → CONTEXT.md + первые ADR.
7. Параллельно: Design OS (отдельный воркспейс) + API-контракт/схема БД.
8. `ui-kit` сразу после экспорта Design OS.
9. Цикл по фичам: `to-tickets` → (`to-spec` для рискованных) → `implement` → `code-review` → мерж с `Closes #N`.

---

### Что мы сознательно не используем — и почему

`wayfinder`, `triage`, `to-questionnaire`, `wait-what`, `ask-matt`, `teach`, `domain-modeling`, `codebase-design` — все они рассчитаны либо на команды больше двух человек, либо на процессы длиннее 48 часов. Для нас это лишний слой поверх и так небольшого проекта.
