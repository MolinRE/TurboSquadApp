# Backend

The backend uses EF Core with PostgreSQL. Set `ConnectionStrings:Postgres` in local configuration or through `ConnectionStrings__Postgres`. Set the database credentials with `POSTGRES_USER` and `POSTGRES_PASSWORD`; keep secrets out of the repository. The default connection string points at the Supabase transaction pooler (port 6543) with `No Reset On Close=true`: the pooler does not answer the `DISCARD ALL` that Npgsql sends when it reuses a pooled connection, and the query hangs.

Docker Compose sets `Database__MigrateOnStartup=true`, so it applies committed EF Core migrations before seeding. For a manual backend run, apply migrations yourself.

After restoring packages, create and apply migrations with:

```bash
dotnet ef migrations add Initial --project back --output-dir Data/Migrations
dotnet ef database update --project back
```

`DatabaseSession` uses `AppDbContext` directly. The project does not add Unit of Work or a generic repository.

For authentication, set `Jwt__Key` to a random value of at least 32 characters. Optional settings are `Jwt__Issuer`, `Jwt__Audience`, and `Jwt__ExpirationMinutes` (1–1440, default 60). The login endpoint is `POST /api/auth/login` with `username` and `password`; it returns a Bearer token. Registration is available at `POST /api/auth/register`.

The voice pipeline reads `POLZA_API_KEY` and `LAYA_API_TOKEN` (`LAYA_API_KEY` is accepted as a local alias). Optional `Voice__PolzaBaseUrl`, `Voice__SttModel`, `Voice__LayaEndpoint`, `Voice__LayaModel`, `Voice__LlmModel`, `Voice__LlmReasoningEffort`, `Voice__LlmMaxTokens`, `Voice__LlmTimeoutSeconds`, `Voice__MinimumConfidence` and `Voice__MaxAudioBytes` override the defaults. During local development the root `.env` is also read for the provider keys; it is ignored by Git.

To seed the three demo accounts, set `DemoAccounts__SeedOnStartup=true` and provide `DemoAccounts__conductor-star__Password`, `DemoAccounts__conductor-novice__Password`, and `DemoAccounts__manager-methodologist__Password`. The seed is idempotent and adds missing roles without replacing existing passwords. `GET /api/auth/me` requires authentication; the manager and methodologist role checks are available under `/api/auth/role-check/manager` and `/api/auth/role-check/methodologist`.

In development, Swagger UI is available at `/swagger`, backed by the OpenAPI document at `/openapi/v1.json`. Use the **Authorize** button with `Bearer <token>` to call protected endpoints. The documentation routes are enabled only in development.

Starter content is seeded on startup: the shift-start event, situations №6 and №33 and trip settings from `Content/Seeds/*.json`, the scale and service-class directories from `ContentDirectory.Default` in `Events/ContentDirectory.cs`, and 15 published swipe questions from `Content/Seeds/questions.json`. Seed events must pass the event validator, otherwise startup fails; only missing records are added, so restarts create no duplicates and methodologist edits are kept. Apply migrations first; to start without a database, set `ContentSeed__SeedOnStartup=false`.

The trip engine lives in `Trips/`. `TripEngine.Reduce(state, action)` is a pure reducer with no database, HTTP or clock: actions are `StartTrip`, `ChooseVariant`, `TimeOut` and `ChooseProactive`. A rejected action returns the same state and a `Rejection` with a reason code, for example a variant hidden by a condition, a timeout on a step without a timer, or a move after the trip has ended. The engine refuses to start with content that fails the event validator or does not match the trip settings. `TripState.Choices` lists the current step's variants with the conditions that hide them. `Debrief.Build` produces layer A of the debrief from the journal after arrival or failure.

The trip API is under `/api/trips` and requires a Bearer token; a trip is visible only to its owner. `POST /api/trips` starts a trip on the latest published event versions and pins its content: event versions by reference, the scale and class directories and the trip settings as a snapshot, so later edits change neither running nor finished trips; `GET /api/trips/{id}` returns the state with only the variants the conductor may choose and the step timer's `expiresAt`; `POST /variant`, `/timeout` and `/proactive` are the moves, and `/variant` and `/timeout` carry the `eventId` and `stepId` being answered, so a repeated click on a passed step is rejected with `StaleStep`. A voice Step exposes no variants and accepts `POST /api/trips/{id}/voice` as multipart fields `eventId`, `stepId`, `attemptId` and `audio`; the server streams the audio to GigaAM-v3, sends the transcript and structured choice criteria to Laya, and returns the Laya reaction as a pending idempotent attempt. Laya returns the selected choice, normalized politeness score, four role-stage probabilities and the safety-violation probability; these are persisted with the Event id, version and Step id. `GET /api/trips/{id}/voice/{attemptId}/reply` then streams only Qwen `delta.content` as SSE; the graph decision is persisted when the reply completes. A provider error or confidence below the configured threshold returns 422, records the attempt, and leaves the Step unchanged; Qwen timeout, provider error, client cancellation and broken SSE are explicit reply errors without an alternative branch; audio is never persisted. `GET /debrief` returns layer A after arrival or failure, including the full Laya assessment, component latencies and passenger replies. Managers can query `/api/analytics/voice` for STT/Laya/LLM latency percentiles, uncertain-decision rate, the explicit zero product-fallback rate and per-Step/Event-version slices. The server owns the timer: an answer later than the timer plus a 1 s tolerance follows the timeout branch, and `/timeout` before expiry is rejected. Engine rejections return 409 with a `reason` code. The trip state is not stored: `TripService` replays the `trip_journal` rows through the engine on the pinned content. Tables `trips` and `trip_journal` come from the `AddTrips`, `AddVoiceAttempts`, `AddPassengerReplies`, `ClaimPassengerReply` and `AddVoiceScoring` migrations.

The swipe shift API is under `/api/swipe-shifts` and follows the screen contract `front/src/lib/swipes/contract.ts` field for field; it requires the conductor role, and a shift is visible only to its owner. Questions (`questions` table, PRD §9.1) are shared with the future Blitz and CMS: a type (`single`, `multiple`, `sequence`, `swipe`; only swipes are played), options per type as jsonb, explanation with key fact, quote and source, topic, categories, service classes, base frequency and status; drafts never get into a deck, including the next cycle and work on mistakes. The rules live in `Swipes/ShiftRules.cs` (`ShiftPlay`), the same as the screen's fake module: a wrong answer or «Не знаю» in the calm mode returns the card after 3 cards, at most twice; «Не знаю» costs half of the wrong side's penalties rounded toward zero; a mandatory scale at its threshold ends the shift. `POST /api/swipe-shifts` starts a calm or woodpecker shift of up to 10 published questions in random order with the first card shown; an answer carries the `questionId` it answers, so a repeated answer is rejected with `StaleCard`, and it does not return the next card: `POST /next-card` shows it and starts its time, idempotently. Answer time runs from the end of the statement typing (35 ms per character; 35 → 21 → 12 in cycles) by the server clock. In woodpecker cycles the card limit is 10 → 7 → 5 s; `/timeout` before the limit minus 1 s is rejected, and an answer later than the limit plus 1 s is recorded as timed out. `/next-cycle` starts the same deck in a new order with the previous cycles' results, `/work-on-mistakes` starts a calm shift of the questions with mistakes, also after a failure. Rejections return 409 with a `reason` code. Like the trip, the shift state is not stored: `SwipeShiftService` replays the recorded verdicts and scale changes of the `swipe_answers` rows on the deck and the scale snapshot taken at the start, so a later edit of a question does not rewrite past shifts. Tables `questions`, `swipe_shifts` and `swipe_answers` come from the `AddQuestionsAndSwipeShifts` migration.
